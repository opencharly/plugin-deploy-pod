# 2026.330.1320 — fix(pod): carry the image on every PrepareVenue state patch

## Summary

An `add_candy:` overlay build with **no authored `engine:` selector** wrote a `PrepareVenue` state
patch carrying only `resolved_image`. `applyDeployState` persists that unconditionally, the node-form
writer emits a `pod:` body (it classifies on `resolved_image`) with **no `image:`**, and the loader
then drops the entry (`ValidateDeployRequiresBox`). The degraded load makes `SaveDeployConfig`
refuse **every** later write to the host config:

```
charly: error: … refusing to write /home/<user>/.config/charly/charly.yml — it holds 2 deploy
entr(y|ies) but only 1 load; this binary would erase the 1 a degraded load dropped
(fix the config first, e.g. `charly migrate`, or remove it to regenerate)
```

That message names two remedies and **neither can be executed** for this entry: `charly deploy reset
<name>` mutates only the loaded map (no-op), and a bare `charly deploy reset` deletes the whole file,
taking the good entries with it. The host is locked out of `charly config` until the file is
hand-edited.

The fix: the patch carries `box` + `target` on **every** emitted state, not only the engine path.
`baseName` was already in scope at the call site.

### Spike — the three candidates for this cause

| Candidate | Verdict |
|---|---|
| **A — the patch always carries `box`/`target`** | **winner**: the entry is complete at write time, so the loader keeps it and the guard has nothing to refuse. Proven by the new test below, which FAILS without this change. |
| B — `applyDeployState` refuses to persist `ResolvedImage` on an entry with no `Image` | rejected: it converts silent corruption into a hard error at a different layer, still leaves the state patch wrong, and does nothing for entries already written. |
| C — back-fill `image:` from `resolved_image` at load | rejected: `resolved_image` is the OVERLAY ref; back-filling it as the entry's image records the wrong box and the next rebuild resolves from it. |

### Candidate C, measured (R12)

C would back-fill `image:` from `resolved_image` at load. Run against a fixture whose only key is an
overlay ref, the entry loads with the OVERLAY as its image — i.e. C records the wrong box:

```
$ CHARLY_DEPLOY_CONFIG=/tmp/fleet-c/charly.yml charly deploy show x
...
        image_backed: true
        image_context: true
        bracketed_lifecycle: true
    image: broken-overlay:cabc723f3910
$ echo $?
0
```
So C FAILS its requirement: it loads the entry, but with the overlay ref recorded as the image — the
next rebuild resolves from the wrong box. (The command exits 0 because `deploy show` prints; what
fails is C as a fix, not the command.)

### Candidate B, spiked (R12)

B would add a guard in sdk's `applyDeployState` refusing to persist `ResolvedImage` on an entry with
no `Image`. sdk ALREADY has such a guard for the degraded-load case, and its own test is green — so
B's outcome is measurable as "the refusal the operator actually hit":

```
$ cd sdk && go test -run TestSaveDeployConfigRefusesADegradedLoad ./deploykit/
ok  	github.com/opencharly/sdk/deploykit	0.011s
$ echo $?
0
```

That is the guard WORKING — and it is exactly the `refusing to write … only 1 load` wall in the
issue. A guard-only fix therefore leaves the state patch wrong and the operator locked out; it
converts silent corruption into the error already observed. B is rejected on that run, not on taste.
