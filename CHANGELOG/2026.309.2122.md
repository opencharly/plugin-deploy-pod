# 2026.309.2122 — fix(pod): refuse a runtime handler the venue cannot launch

## Summary

`charly config` for a `pod:` deploy on `engine: containerd` emitted a systemd unit whose
`ExecStart` named a runtime handler chosen from the CAPABILITY ROW alone
(`engineDefaultRuntime` → `RuntimeHandlers[0]` → `crun`) and never asked the VENUE whether it
can launch it. On a venue whose containerd has no `crun`, the daemon rejects the unit, systemd
restart-loops, the failed attempt leaves the container `CREATED` with its name held, and every
retry dies `name-store error: name ... already used` (opencharly/plugin-containerd#16).

This change consults the venue:

- `venueRuntimeHandlers()` (`candy/plugin-deploy-pod/engine_ops.go`) reports the subset of the
  engine's DECLARED handlers this venue can launch, asking the SAME resolution the launch
  performs: `exec.LookPath` over the runtime executable, mirroring nerdctl's
  `generateRuntimeCOpts` (a bare word is the OCI-runtime binary) and containerd's
  `pkg/shim.BinaryName` (a runtime type is `containerd-shim-<second-last>-<last>`).
- `ensureVenueRuntimeHandler()` refuses the config/start step when the selected handler is not
  in that set, naming (a) the handler charly selected, (b) the handlers the venue reports, and
  (c) the remedy: install the runtime on the venue (`layer-containerd` installs crun and krun)
  or point the deploy at a venue that has it. It refuses instead of falling back to another
  handler — a silent switch to a different OCI runtime is a different substrate (R3).
- It runs at `runPodConfigSetup` (before any file is written or image work runs), at
  `runConfigDirect`'s launch, and at `resolvePodStartDirect` (start). An engine with an empty
  `runtime_handlers` list (podman, docker) takes exactly today's path: no probe, no
  `--runtime`, no new failure mode.
- A failed start now cleans up: `podContainerStart` stops the unit (so `Restart=always` cannot
  re-create the container) and removes the partial container through the SAME teardown argv
  `charly remove` uses (`engineRemoveArgv`); `runConfigDirect` removes it on a failed launch
  too. `resolvePodStartPlan` now returns the selection it built the plan from, so the cleanup
  addresses the same address/namespace the launch used.

Measured, not assumed: on this host (rootless containerd 2.3.5, nerdctl 2.4.1) `nerdctl info`
carries no `Runtimes` map in either mode; the resolution nerdctl actually performs for a bare
`--runtime` word is `exec.LookPath`, which is what the probe mirrors.

The second copy of the default (`plugin-containerd/candy/plugin-containerd/plugin.go`,
`defaultRuntimeHandler = "crun"`) is not on this code path and is not changed here; it is
tracked by the same issue #16, which now carries this PR's evidence.

Refs opencharly/plugin-containerd#16 — the issue lives in another repository and is NOT closed
by this PR; this PR fixes the pod substrate's consumer side of it.

## Change classification

- **Kind:** runtime behavior fix in the `pod` deploy substrate (config emission, direct
  launch, start cleanup). No schema, flag, wire, or pin change; `charly box validate` still
  checks the same candy and deploys.
- **What a consumer sees:** a containerd deploy whose venue cannot launch the selected handler
  now fails `charly config`/`charly start` with the selected handler, the venue's handlers and
  the remedy, instead of writing a unit that can never start; a venue that has the handler
  produces the same argv as before.
- **Breaking change + rollback:** no schema or emitted-artifact shape changes; the one
  deliberate behavior change is the loud refusal on a venue that cannot launch the handler
  (previously a unit that restart-looped and poisoned the container name). Rollback: revert
  this commit — no state, schema, volume, or generated artifact migrates, and any unit already
  written stays exactly as it is.
