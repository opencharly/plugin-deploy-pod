## Summary

`plugin-deploy-pod` serves the `deploy:pod` substrate. Every shell step it drives on the venue went
through `exec.VenueRunSilent`, which **discards both streams** of the command it runs — so a failure
at the process boundary reached the operator as a bare `command exited 125`, with nothing naming the
image, the reason, or the venue. That is the diagnosability defect of
`opencharly/plugin-deploy-pod#19`, and it is the same class of loss that left
`opencharly/opencharly#322`'s orphaned bed pod unattributable: charly has a rich catalogue of failure
causes and a habit of discarding them exactly where they cross a process boundary.

The cure is not a new mechanism and not a `spec` change: `VenueCapture` — the sibling primitive over
the SAME reverse channel — already returns the venue's trimmed stderr
(`spec/exec/executor.go:213`). The defect was that the code kept choosing the primitive that drops
it (`:229`). This change:

- adds **one** helper, `venueRun(ctx, ex, script, label, target)` in the new `venue_exec.go`, which
  runs the step with the CAPTURING primitive and returns the venue's own cause behind the operation
  and the target;
- routes **all 8** venue call sites through it (`lifecycle.go` ×5, `overlay.go`'s overlay build and
  deploy-name alias tag, `volume_root.go`'s named-volume reconcile) and **deletes** the old
  `execErr` helper it replaces — one path, so no future call site can lose a cause;
- declares the seam as an interface holding **both** primitives, so a test pins *which* one is used
  and a future reader cannot silently swap the capturing call for the silent one.
