## Summary

**A secret reaches a service's ENVIRONMENT without ever entering the plan — and the overlay path it
replaces is a named, testable function instead of three inline calls.**

`DESIGN.md:2511` (D-SEC-1) forbids a secret entering "the store, artifacts, labels, the IR, **state** or
output". `Op.Env` **is** the IR — a variable baked into the rendered script at PLAN time. **A container's
`Env:` is written at CONFIG time, host-side.** The same secret can reach the process either way; only one of
those paths puts it in the IR.

**Stated without inflation: this PR takes the value out of the IR.** It does **not** satisfy D-SEC-1's
`state` limb — `config_setup.go:437` passes `Env: envVars` into the config writer, which persists
`Environment=` into the deployment's unit. **That is tracked as #75**, whose fix is the `type:secret` owner's
`bind` returning an `#Opaque` handle (`spec/schema/bind.cue:48-52`, `DESIGN.md:685`).

### 1. The overlay step is a named function

```diff
-	candyList := deploykit.SelectCandiesForPlans(plans, dg.Candies)
-	secretEnv := deploykit.ResolveSecretForCandy(candyList, deploykit.CredentialAccessViaExecutor(ctx, exec))
-	deploykit.InjectSecretsIntoPlans(plans, secretEnv)
+	deliverSecretEnv(plans, dg.Candies, deploykit.CredentialAccessViaExecutor(ctx, exec))
```

A byte-for-byte MOVE, with identical suite results before and after. It exists so a harness can **drive the
function** rather than observe a plan set: the plant fails *at the code path that would ship the call*.

### 2. The entry point — the deploy's BOX, not the image it runs

```go
func deployBoxBase(uf, dc, box, instance) string {
	if _, isBox := spec.BoxConfigFrom(uf.Box, box); isBox { return box }   // the deploy's own box wins
	if node, found := dc.Deploy[spec.DeployKey(box, instance)]; found && node.Image != "" {
		if _, imageIsBox := spec.BoxConfigFrom(uf.Box, node.Image); imageIsBox { return node.Image }
	}
	return box
}
```

`c.Box` is **definitionally** a box — `loadUnifiedForBox` resolved the project with it. `node.Image` is the
image the deploy runs: a box name for a box-based deploy (`check-pod-overlay`'s `image: check-k8s-deploy-app`
**is** a box), but `quay.io/fedora/fedora:43` for a registry deploy, which names no box. **Preferring the
image started the walk from a ref that resolves to nothing and silently delivered no secrets.**

### 3. The chain walk, the union, and the scoped resolve

`boxCandyChain` follows `Base`/`From` over `spec.BoxConfigFrom(uf.Box, …)`. `DeployCandyChain` adds D-CAP-6's
union:

> **D-CAP-6** (`DESIGN.md:695`): *"The needs and uses of a deployment are the union of those of **the
> deployment, its box and all their candies**."*

`add_candy:` candies run in the container and can author `secret_require:`, so a box-chain-only seam
**under-resolves the overlay idiom this project's own pod bed uses**. **Known limit:** an `add_candy:` value
is a REF (`@github.com/opencharly/layer-ripgrep:v2026.235.1653`), and resolving it to the candy NAME requires
reading that repo's manifest — which the config-time seam does not yet do. The union is contract-correct and
**not yet effective for ref-form overlays**; that is part of #75's scope.

### 4. The hazard this PR is really about

`ResolveSecretForCandy` → `EnsureCandySecret` **auto-generates a 32-byte token when the value is missing
everywhere**. An unscoped resolve at config time would **mint and persist credentials for candies outside this
box's chain** — a side effect on the operator's credential store, triggered by `charly config`.

**That failure would be invisible** until an operator found foreign secrets in their store. So it gets a test:

```
PLANTED (the chain ignored; every candy in raw resolves):
--- FAIL: a candy outside the box chain must contribute nothing,
    got map[string]string{"DB_PASSWORD":..., "FOREIGN_TOKEN":..., "SHARED_TOKEN":...}
```

**Three plant results, each pasted in the commit that introduced it:**

```

--- FAIL: the deploy's OWN box must win over an image that is ALSO a box, got "image-box"

PLANTED (chain ignored):

PLANTED (box chain only, add_candy ignored):
--- FAIL: an `add_candy:` candy IS one of the deployment's candies (D-CAP-6) and must deliver
```

**A FOURTH plant, and it is the loop's own proof:**

```
PLANTED (the visited set removed, `if next == base` restored):
--- FAIL: boxCandyChain did not terminate on a cyclic chain: `charly config` would HANG
```

**The first version tracked only CANDY names, and its only guard was `if next == base` — which catches `A -> A` but not `A -> B -> A`.** A two-box cycle revisits boxes whose candies are already collected, so the candy-level set never fires and the loop spins forever. **The gate for a malformed manifest is validation's; this function's obligation is to terminate**, because a `config` command that hangs is worse than one that reports a bad chain.

**Three fixtures, three lessons — plus a fourth about loops.** Each of the first two passed against the implementation it was written to
catch until the fixture was made *discriminating*; the third could only fail once the overlay candy was
reachable **only** through `add_candy:`. **A fixture whose branches agree cannot test a choice between them**,
and **a fixture built from the implementation's expectations inherits its blind spot.**
