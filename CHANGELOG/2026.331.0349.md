# 2026.331.0349 — fix(cdi): keep-id GPU units put the injected driver libraries on LD_LIBRARY_PATH

## Summary

A keep-id GPU unit carries a **devices-only** CDI spec: the plugin keeps the host spec's
`deviceNodes`, drops its `mounts` (they fail under keep-id with `mount_setattr … EPERM`) and drops its
`hooks`, and recreates the driver libraries as read-only binds. Dropping the hooks also drops the one
step that refreshed `/etc/ld.so.cache` at container start, and the binds land in a directory the
cache never learned about.

Measured inside the two shapes on `charly-rtx4080`:

| | stock spec (no bind volume → no keep-id) | derived spec (bind volume → keep-id) |
|---|---|---|
| `/etc/ld.so.cache` mtime | **container start** | **image build** |
| `libcuda` entries in the cache | **4** | **0** |
| `libcuda.so*` files present | yes | yes (bound at `/usr/lib`) |

So a consumer that resolves the driver **through the cache** fails while a direct `dlopen` user still
works — which is why the failure looked application-specific. `triton/backends/nvidia/driver.py`
`libcuda_dirs()` reads `ldconfig -p`, then falls back to `LD_LIBRARY_PATH`, and asserts:

```
qwen3-tts-worker: synth failed: AssertionError('libcuda.so cannot found!
Please make sure GPU is set up and then run "/sbin/ldconfig" (requires sudo) to refresh the linker cache.')
```

with `/usr/lib/libcuda.so`, `.so.1` and `.so.615.78.08` all present in that very container.

The fix names the injected directories on `LD_LIBRARY_PATH`: the loader honours it, triton accepts it
explicitly, and it is derived from the same bind list — nothing is hard-coded. It is emitted by **all
three** emitters (the quadlet config, the direct launch, the transient `charly shell` container), goes
to the **front** of the value with any image-provided path preserved, and is **idempotent** (a dir the
value already carries is not added twice, so a config that is then turned into argv keeps one copy).
