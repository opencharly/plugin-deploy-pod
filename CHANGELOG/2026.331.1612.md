# 2026.331.1612 — fix(bed): assert the keep-id CDI contract, and pin a base tag the registry has

## Summary

`check-pod-cdi-userns` was red for two independent reasons, and both live in this one file.

**1. Its subject could not be created.** `pod-cdi-keepid-bind` pinned
`ghcr.io/opencharly/arch:2026.323.1515`, which the registry answers with `MANIFEST_UNKNOWN`
(`opencharly/plugin-deploy-pod#103`), so `charly config` died at ensure-image before the bed exercised
anything. The base is now `2026.307.1828`, the tag the repo actually carries.

**2. Its assertions described a retired contract.** The bed required
`UserNS=host` and `User=0:0`, and FAILED on any unit carrying `UserNS=keep-id` — while the merged
contract (`feat/keepid-cdi-spec-v2`, D-HW-10, and `layer-cdi`'s rule that a bind-mounting unit runs as
the image user under `keep-id`) emits keep-id with the image user against a **derived devices-only CDI
spec**. The bed was green on the shape the plugin no longer emits, and red on the shape it does — it
asserted the wrong world in both directions.

The assertions now read the contract's own lines out of the emitted quadlet:

```
grep -q '^UserNS=keep-id:uid=1000,gid=1000$' "$UNIT"
grep -q '^PodmanArgs=.*--cdi-spec-dir '      "$UNIT"
if grep -q '^User=0:0$' "$UNIT"; then … exit 1; fi
```

The step's prose, its `id:` (`pc-userns-host-root` → `pc-userns-keepid-user`), the bed's header comment
and the "no keep-id" aside inside the step are rewritten with them, so the file states ONE contract
instead of two (R5's claim sweep: the aside asserted the opposite of the assertion beneath it).

**One addition, measured, bounded.** A readiness probe before the bind write. On a RESTARTED unit
`charly start` returns before the container's mounts are visible, so an immediate
`charly cmd … test -d /data` fails (`opencharly/charly#1301`); the loop polls to a 60 s deadline, never
a fixed sleep, and a bind that never appears still fails the step.
