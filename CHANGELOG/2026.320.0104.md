# 2026.320.0104 — fix(deploy): a missing required secret names its coordinate and its store state

## Summary

Head `db11ae94331aaf7f1eb39afd4e101eec71610b07`, based on `origin/main` `1417167` (0 behind, 1 ahead):
` 3 files changed, 304 insertions(+), 21 deletions(-)`.

`checkMissingSecretRequires` decided everything from `Resolved` and **discarded the resolver's `Source`**,
so three different failures rendered as one message that told the operator to store a value:

| what happened | what the operator was told |
|---|---|
| the credential is genuinely absent | store it — correct |
| the keyring is LOCKED (needs an interactive unlock) | store it — they re-store a credential they already have |
| the keyring is UNREACHABLE (no session bus / broken collections) | store it — the store can never be read |

and the message never named the coordinate it had queried, although the dependency carries it (`dep.Key`,
e.g. `charly/api-key/qdrant`). That is what made opencharly/sdk#526 un-triageable: its field report is this
error beside a `charly secrets get charly/api-key qdrant` that returned a 44-char value, and the remedy the
reporter found was to seed the DEFAULT coordinate — a silent second copy that then masks the real state.

### What the report does now (`missingSecretReport`, pure)

- **Names the coordinate** for every unresolved required secret, rendered by the SAME `secretKeyForDep`
  split the resolver queries with, so the report cannot disagree with the lookup.
- **Splits by source.** `locked` / `unavailable` produce a distinct `could not READ the credential store`
  section with the remedy that fits (unlock, or start a provider / pin `secret_backend config`) plus a
  copy-pasteable `charly secrets get <service> <key>` — and **no store-it advice**.
- **Keeps today's advice** exactly when the store WAS readable and the coordinate is empty.
- **Reports both classes** when a deploy hits both, with the unreadable class as the returned error.

### The R10 bed this PR adds — the answer to the validator's first BLOCK

`go test` is not the change-class gate for runtime code, and the reviewer was right that neither changed
branch had executed. The new `check-pod-secret-diagnostic` bed follows this repo's own self-gating idiom
(the `check-pod-ensure-gate` shape): a `disposable: true` pod subject whose labels declare a required
credential at an explicit coordinate, a `kind:local` template composing THIS repo's candy, and a plan that
drives the REAL `charly config` twice — Arm A with the keyring backend pointed at a session bus that does
not exist (`unavailable`), Arm B with the config backend over an empty XDG dir (readable, coordinate empty
→ `default`) — asserting each arm's message.
