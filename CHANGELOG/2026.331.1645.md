# 2026.331.1645 — fix(pod): a start waits for the container to be RUNNING, not just for the command to return

## Summary

`charly start` on a pod unit ran `systemctl --user start <svc>` and returned as soon as the job was
queued. The engine then **creates** the container and only afterwards starts it — and a
created-but-not-running container has an **empty mount namespace**: `podman exec` into it succeeds and
sees none of its mounts. So `start` returning 0 did not mean the container was up, and a caller that
touched a bind-mounted path immediately raced it (`opencharly/charly#1301`).

```
charly start <pod>                 → rc=0
charly cmd <pod> "test -e /data"   → rc=1   ("No such file or directory")
…                                    PRESENT ~1.6s later (measured below)
```

**Measured on the real unit** (`pod-cdi-keepid-bind`, keep-id + CDI + a bind at `/data`), three
consecutive runs before the fix:

```
fresh create:  start rc=0 → immediate test -e /data = PRESENT
restart #1:    start rc=0 (1778ms) → /data ABSENT at +0ms, PRESENT at +1645ms
restart #2:    start rc=0 (1748ms) → /data PRESENT at +1ms      (the race did not fire)
```

The window is real and **intermittent** (1.6 s here, ~11 s in the filing), which is exactly why the fix
is a bounded wait on the engine's own state and not a delay.

### The fix

- **`start_ready.go`** (new) — `waitContainerRunning` / `pollContainerRunning`: inspect
  `{{.State.Status}}` until the container reports `running`, 1 s cadence, 10 s per attempt, 60 s
  deadline, through the shared `poll.PollUntil` primitive (the same one the declared-readiness wait
  uses). A failed inspect is transient (not created yet, or the engine still replacing it); the
  deadline is what fails a container that never comes up.
- **`readiness.go`** — `startEngineBin` is now the ONE resolution of the engine binary (host-supplied
  param first, then the plan's), used by both waits (R2: it was inlined twice).
- **`lifecycle.go`** — `podStart` calls the wait immediately after `podContainerStart`, before the
  declared readiness probe, the tunnel and the caller.

The wait is deliberately separate from the declared readiness wait: that one waits for the
**application** to accept work and only runs when the deploy authors a `probes.readiness`; this one
waits for the **container** to exist and always runs.

**The four new tests, and the one that is the change's own discriminator:**

- `TestPollContainerRunning_WaitsThroughCreatedUntilRunning` — a venue reporting `created, created,
  running` must be inspected **at least three times**. A single read is exactly the defect; this test
  fails if the poll returns early.
- `TestPollContainerRunning_FailsAContainerThatNeverRuns` — a container stuck at `created` fails the
  wait instead of hanging or passing.
- `TestWaitContainerRunning_InspectsTheContainersOwnState` — the inspect names the container.
- `TestWaitContainerRunning_RefusesAPlanWithNoContainerOrEngine` — refuses rather than silently
  skipping; a start that cannot be waited on is the bug.
