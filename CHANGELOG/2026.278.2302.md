# 2026.278.2302 — fix(deploy-pod): reconcile named-volume roots to the runtime user

## Summary

A podman named volume's root directory keeps the ownership it had when the volume was **first populated**, and no deploy ever reconciles it. podman sets that ownership only while it populates an *empty* volume (the documented copy-up, which mirrors the image's directory at the mount path through the container's userns); a volume that is already **non-empty** is attached exactly as it is — contents *and* root ownership. So a volume first populated from an image revision whose directory was root-owned keeps a root-owned root for every later deploy of that (deploy, volume) pair, even after the image is corrected: its contents are correctly owned while its root is not, and a runtime user of uid 1000 cannot create its own files there.

That is a live failure, not a theory: `charly check run check-githubrunner-pod` died in the runner's `config.sh` with

```
Unhandled exception. System.UnauthorizedAccessException: Access to the path '/home/user/actions-runner/_diag' is denied.
command "cmd": exit code 134
```

because the bed's `state` volume had been populated weeks earlier from an image whose `/home/user/actions-runner` was root-owned. Both the state and the failure are reconstructed on demand below, so this is measured here, not only reported on the issue. Measured on the host, before the fix, on the surviving volume from that run:

```
$ stat -c '%n uid=%u gid=%g mode=%a' .../volumes/charly-check-githubrunner-pod-state/_data
.../charly-check-githubrunner-pod-state/_data uid=1000 gid=1000 mode=755      # container root; NOT the runtime user
$ stat -c '%n uid=%u gid=%g mode=%a' .../volumes/charly-check-githubrunner-pod-storage/_data
.../charly-check-githubrunner-pod-storage/_data uid=100999 gid=100999 mode=755 # correct
```

and the engine's behaviour reproduced deterministically with throwaway runs of the same image (cleaned up afterwards): a fresh volume and a pre-existing-but-empty volume both come out `100999`; only a pre-existing non-empty volume is left untouched. Re-running an existing deploy is the normal case, not an edge case: removing a deploy keeps its named volumes — `plugin-pod`'s `--purge` flag is spelled `Also remove named volumes` (`pod_cmd.go:173`) and gates the only caller of `removeVolumes` (`remove_orchestration.go:444`, `:467`) — so a bed is not hermetic after a failed or aborted run.

**The fix.** `charly config` now reconciles every named volume's root to the deploy's **runtime user**, before either emission path (the direct return and the quadlet write) creates the container: the deploy image is run once per named volume as the container's root — the image's own user does not own the volume root and cannot chown it — and the volume's root is then given to that user with a bare `chown <uid>:<gid>`. The volume is mounted at a scratch path rather than its real container path, because mounting an *empty* named volume where the image has a directory sets off the engine's copy-up: a repair meant to change only the root's ownership must not populate the volume as a side effect.

The target is the runtime user, deliberately, and not "copy the image directory's owner onto the root": the latter would reproduce the state being repaired whenever that directory is itself root-owned, which is exactly how the failure above arose. And the command is not built through a shell — the argv *is* the command, with `chown` as the container's `--entrypoint`, so its operands are the deploy user's two integers and a package constant; a volume name or image reference carrying `$`, a backtick or any other metacharacter has no shell in that container to interpret it. (An earlier form of this patch interpolated the volume's container path into a `sh -c` script with Go's `%q`, which is a Go string quoter and not a shell quoter — it leaves `$`, backtick and `!` live inside the double quotes it emits, so a path such as `/x$(cmd)` was command-substituted inside the container. The reviewer was right about that; the fix is to remove the shell, not to quote harder, and `TestVolumeRootReconcileArgsIsShellSafe` now pins the property.)

Two deliberate details:

- **keep-id deploys are left alone.** Under `--userns=keep-id:uid=N,gid=N` the volume's owner *is* the runtime user, so there is nothing to repair — and this helper, whose container root is the host user, could only write an owner that a keep-id runtime could not use. Standing aside is decided by one predicate over every emitter that can create the deploy's container, not by one engine test. Three emitters carry a keep-id flag and they do not test the same things: `GenerateQuadlet` keys on the bind mounts alone (quadlets are podman-only), `directPodmanArgs` — the argv `charly config` execs in direct mode, which is podman by construction because `runConfigDirect` hardcodes `exec.Command("podman", ...)` (`config_setup_helpers.go:534-537`) — keys on the deploy user, and `buildStartArgs`/`buildShellArgs` key on the engine. Each now names its own condition, and `volumeRootKeepID` is the union over the emitters of the deploy's mode, so the reconcile stands aside exactly when one of them emits keep-id, and the drift guard compares that union against the real renderer output and the real argv.
- **A failure is fatal, not best-effort, and the requirement it states is the real one.** The requirement on the image is a **POSIX `chown`** — present in every standard distribution image and in BusyBox — and nothing else: no shell, and no GNU `--reference`, so the helper asks strictly less of the image than the alternatives did. A deploy image without a `chown` now fails at `charly config` with a named error instead of proceeding to serve a volume the runtime user cannot write into, which would surface later as the application's own crash far from its cause (the measured exit=134). That is a deliberate behaviour change, stated here rather than discovered later: failing where the ownership could not be established is the honest outcome, and it is preferable to the silent alternative.

Files: new `candy/plugin-deploy-pod/volume_root.go` (+ `volume_root_test.go`); one call in `config_setup.go`; the keep-id conditions of `config_setup_helpers.go` (`buildStartArgs`, `directPodmanArgs`) and `resolve_f12.go` (`buildShellArgs`) now come from the named predicates instead of being repeated.

Closes #23.

**The injection the reviewer found, demonstrated against the code that had it.** Go's `%q` is a Go string quoter, not a shell quoter: inside the double quotes it emits, `$`, a backtick and `!` are all still live to `/bin/sh`.
