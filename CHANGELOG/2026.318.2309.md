# 2026.318.2309 — fix(config): pass the operator's -p pins into port resolution (first-run pin was silently dropped)

## Summary

A port pin supplied on the command that **first** configures a deploy was accepted, printed, and silently
dropped:

```
$ charly -C distro-fedora config openwebui -i lab -p 18080:8080
PublishPort=127.0.0.1:8080:8080          # ← the auto-allocation, not 18080
```

Re-running the **identical command** honoured it — which is exactly what hid the bug: the entry had meanwhile
recorded `port: ["18080:8080"]`.

**Mechanism.** `config_setup.go` resolves ports *before* merging the CLI overrides:

1. `resolveDeployPorts(…, &meta)` computes `ResolvedPort` from the image label's container ports plus the
   **entry's** `port:` pins (`sdk/kit/ports.go:350` honours a pin for its container port);
2. `MergeDeployOntoMetadata` → `ports := meta.Port`;
3. `kit.ApplyPortOverrides(ports, c.Port)` applies the CLI pins **last**.

On a fresh deploy the entry has no pins at step 1, so an allocation is persisted as `resolved_port` — and the
quadlet publishes **that**. The override from step 3 never reaches the artifact.

**Fix.** The operator's pins ride *into* the resolver: `resolveDeployPorts` takes a variadic `cliPins …string`
(the twelve existing call sites keep compiling) and merges them after the entry's pins — CLI last, matching
`ApplyPortOverrides`' precedence — so the first resolution already lands the operator's host port.

Refs plugin-deploy-pod#52.
