## Summary

A pod deploy that carries a **CDI GPU device AND a bind volume cannot start**. `keep-id` was emitted for *any* bind
mount (`engineKeepID(engine, len(bindMounts))`), and crun cannot apply the CDI device's ~62 FILE mounts inside a
keep-id user namespace, so the container dies at the first one:

```
Error: crun: mount_setattr `/usr/bin/nvidia-cuda-mps-control`: Operation not permitted: OCI permission denied
```

Measured today on this host (podman 6.2.0, crun 1.31, rootless, overlay), against **two different images** so the
image is ruled out: `--device nvidia.com/gpu=all` alone rc=0; `+ --userns=keep-id` rc=126; `keep-id:uid=0,gid=0` rc=126;
`+ --group-add keep-groups` rc=126; with the CDI target paths pre-created in the image rc=126; `--userns=host` + the
device rc=0; `--userns=host --user 0` + device + bind rc=0 with the bind writable and the file owned by the host user.
keep-id without a device, and keep-id with a FILE or DIR bind but no device, is rc=0 — keep-id itself is fine,
keep-id × CDI is not.

**This is opencharly/plugin-deploy-pod#81.** The rule is now in ONE fact, `podCarriesCDIDevice(engine, gpu,
privileged)` = `gpu && !privileged && engineUsesCDI(engine)` — the SAME fact the quadlet renderer has always keyed
its `AddDevice=nvidia.com/gpu=all` on, over the **resolved deploy** and the **capability seam** (`GPUArgStyle ==
"cdi"`). Two things are decided from it and nothing else:

| resolved deploy | mapping | device |
|---|---|---|
| bind mount + CDI device | `userns=host`, workload as container root (`--user 0:0` / `User=0:0`) | `--device nvidia.com/gpu=all` / `AddDevice=…` |
| bind mount, no CDI device (no GPU, **or** privileged) | keep-id, byte-identically as today | none — `--privileged` is the grant |
| no bind mount | mapping left alone — keep-id was never in play | as the GPU fact says |

A **privileged** GPU deploy is in the second row on BOTH sides: `--privileged` already grants every device, the unit
has always skipped `AddDevice=` for it, and the argv now skips the `--device` too (`podGPUArgs`) instead of passing a
device its unit does not carry. That symmetry is what round 1 of this PR's review found missing — see the correction
note under `## How tested`.

Every emitter that can create the deploy's container consults it, so the argv and the unit cannot disagree:

- the engine `start_plan` argv — `directRunArgs` (direct-mode `charly config`), `buildStartArgs` (`charly start`),
  `writeSystemdUnitConfig` (the `systemd-unit` run mode);
- `charly shell` (`buildShellArgs`) and `charly exec` (`buildExecArgs`) — an attach that demoted itself to uid 1000
  could not write the bind the deploy exists for;
- the quadlet `.container` — `UserNS=host` + `User=0:0`, emitted by **opencharly/sdk#591** (tag
  `v0.2026323.1553`, which this PR pins). The renderer cannot import this package, so the drift guard compares this
  decision against `deploykit.GenerateQuadlet`'s **real** output on every row; there is no second copy of the
  condition left in `volume_root.go` (`quadletCarriesCDIDevice`, `quadletKeepID` and the per-run-mode branch of
  `volumeRootKeepID` are deleted, and the reconcile asks `podUserNSFor` like every other emitter).

Two things the rule forced, and both are in this diff rather than assumed: `userns=host` is a REQUEST fact on the
engine `start_plan` (`UsernsHost` + `WorkloadUser`), not a second spelling of flags; and `directRunArgs` now receives
the deploy's GPU fact, which it never did — without it the direct-mode argv carried no device while the deploy's own
config said it had one, so the mapping would have been decided over a device that was never injected.

**`Closes #81`.** The strata pod bed (`opencharly/pod-strata`'s `check-strata-gpu-pod`, opencharly/opencharly#1174) is
the consumer that was blocked; it is not touched by this PR.

## Change classification

One behaviour changes, and it is the one that could not run: a deploy carrying a CDI GPU device **and** a bind mount
is now emitted with `userns=host` + container root instead of keep-id. Bind-only deploys are byte-identical, and a
GPU deploy with no bind mount is unchanged.

**Breaking change + rollback:** the consumer-visible changes are (a) the emitted `.container`'s `UserNS=`/`User=` pair
for a CDI+bind deploy — which could not start before, so no working configuration changes; (b) `charly shell` /
`charly exec` against such a deploy now run as container root, which is the same identity the container itself runs
as; (c) a direct-mode deploy's argv now actually carries the GPU device it already detected; and (d) a **privileged**
GPU launch no longer passes `--device`/`--gpus` — its unit never did, so the argv is now the same shape as the deploy,
and `--privileged` is the device grant (round 1 of this PR's review is what caught this asymmetry). Rollback is
`git revert` of both commits plus a `go.mod` pin back to `github.com/opencharly/sdk v0.2026320.617`; the deploy's unit
is regenerated by the next `charly config`, so nothing is sticky on the host.

**Consumer note (for whoever reads this next):** the deploy path consumes this plugin from `main`, so **nothing needs
a pin bump on our side** — but the plugin's own `require github.com/opencharly/sdk` MUST move to `v0.2026323.1553`,
because the quadlet half is `opencharly/sdk#591`. That bump also raises the transitive
`require github.com/opencharly/spec` from `v0.2026320.16` to `v0.2026322.1814`, which is what the tagged sdk declares;
`go mod tidy` resolves it and it is in this diff.
