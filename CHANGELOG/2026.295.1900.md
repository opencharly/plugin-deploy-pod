# 2026.295.1900 — feat(pod): run pod deploys on containerd through the engine ops

## Summary

The engine word is `containerd` (`spec v0.2026295.1243`), but the pod substrate could not use it: `charly config` accepted only `quadlet`/`direct`, so nerdctl's `systemd-unit` mode was rejected; image staging was pinned to a podman constant; and the generic engine ops (`start_plan`, `unit_emit`) had no consumer in this plugin, so every launch and unit was podman-shaped.

This change makes the pod substrate engine-agnostic by construction:

- **Accept `systemd-unit`** in the config setup and remove paths, and emit that mode's supervision file through `unit_emit`.
- **Route launches through the engine ops** — `start_plan` for argv, `unit_emit` for units — so the capability table supplies the binary, keep-id fact, GPU flag style and runtime handlers. No engine name is switched on in the pod.
- **Remove the podman run-engine constant.** Staging and metadata extraction use the resolved run engine, so the image lands in the store that will launch it.
- **Every containerd launch carries `--runtime`** selected from `runtime_handlers` (`crun` today) and the capability's `--address`/`--namespace` before the subcommand, so it never relies on a daemon default.
- **Rootful:** use `privilege_prefix` where a launch can finish safely; a rootful containerd/systemd-unit target is **refused with the remedy** (rootless staging + system-scope units are not implemented here) instead of being silently run rootless.
- **Start/stop dispatch is explicit on the unit run modes.** `podStartCommand` sends both `quadlet` and `systemd-unit` to `systemctl --user start`, keeps `podman start` for a direct-deploy marker, and refuses an unknown mode rather than exec'ing an empty argv.
- **Bump `spec` to `v0.2026295.1243` and `sdk` to `v0.2026295.1359` together** (the older sdk does not compile against the new spec); `go mod tidy` is idempotent. The sdk bump pulls `github.com/containerd/containerd/v2`, `grpc v1.83.2` and the OTel stack in as **indirect** modules (`go.mod`/`go.sum`, no new direct import in this module).
- **Tests:** a containerd arm (`--runtime` + address/namespace; the emitted unit wraps that argv), a podman control (no containerd-only flags; the same keep-id spelling), the config-path unit write, the rootful refusal, the start dispatch, the resolved systemd-unit start plan, the containerd keep-id fact, and the bare-env refusal. The retired `nerdctl` engine word in `volume_root_test.go` becomes `containerd`.

**Review round 1 — BLOCK at `b2cccc7` (validator `ollama-cloud/deepseek-v4.1-flash`).**

- **Block 1 (systemd-unit start path): fixed and pinned.** The diagnosis (a systemd-unit plan falls into the exec-argv branch) was not reproducible: `podContainerStart`'s `default` arm already sent every non-direct mode to `systemctl`, and `resolvePodStartSystemdUnit` sets `DirectDeploy=false`. The dispatch is now explicit — `podStartCommand` gates on `kit.IsUnitRunMode` for `quadlet` and `systemd-unit`, keeps `podman start` for a direct-deploy marker, and refuses an unknown mode — and two tests cover it: `TestPodStartCommand_UnitRunModesUseSystemctl`, and `TestResolvePodStartSystemdUnit_StartsViaSystemctl`, which runs the real resolver over a unit file and asserts `systemctl --user start 'charly-demo.service'` with an empty `RunArgv`.
- **Block 2 (remove leaves the unit file): rebutted with evidence.** `charly config remove` is documented as disable-only: "`charly config remove` only disables the quadlet service (the quadlet file remains); `charly remove` is the complete teardown (stops the container, deletes the quadlet file, reloads systemd)" (`charly/CHANGELOG/2026.221.2032.md`, reaffirmed in `config_remove.go`'s doc comment). The quadlet branch in the same function performs only `systemctl --user disable --now`, with no file removal. Removing the systemd-unit file would diverge from quadlet and break re-enable; the branch now carries a comment stating the contract.
- **Non-blocking observations, addressed.** A bare `KEY` env entry is now **refused with the reason** instead of silently dropped (`writeSystemdUnitConfig`; `envSliceToStrMap` states why), with `TestWriteSystemdUnitConfig_RejectsBareEnv`. The README now says "one supervision file, plus the tunnel companion unit when configured". `TestEngineKeepID_ContainerdHasNoKeepIDArg` pins the verified capability fact (`containerd` `UsernsKeepIDArg=""`, so nerdctl never receives podman's spelling). The sdk bump's indirect module surface is called out in Summary.

The RCA's missed control: no test resolved a **start** plan, so the validator had to infer the dispatch from an unchanged function; the new resolver test closes that gap.
