# 2026.296.1251 — feat(pod): select the engine through the sdk resolvers and stage images on W3.7 (#41)

## Summary

Migrates `plugin-deploy-pod` — the largest consumer left — onto the sdk's ONE selection model and the W3.7 image store. Every site that read `rt.RunEngine`, re-derived "deploy entry else runtime" by hand, or carried an engine fallback now calls `deploykit.ResolvePodEngine` + `deploykit.ResolveContainerdTarget`; image staging probes `deploykit.NewImageStore` instead of `container.LocalImageExists`.

Pins: `github.com/opencharly/spec v0.2026296.1036`, `github.com/opencharly/sdk v0.2026296.1207` (W3.1 resolvers + W3.7 `ImageStore`/`ResolveImage`).

Behaviour this changes (each pinned by a test that fails on the pre-change tree):

1. A retired/unknown engine word is now a hard error. Before, the deploy entry's word was returned verbatim and `kit.EngineBinary` fed it to `container.EngineCapabilityFor`, which resolves ANY unknown word to the default engine — a `nerdctl` deploy ran podman silently.
2. A per-deploy `namespace:` now reaches the engine argv/unit/store. Before, `engineGlobalArgs` emitted the capability's default namespace only.
3. A per-deploy `rootful:` now reaches the target (and the refusal predicate reads it). Before, the predicate read `rt.Rootful` only.
4. Staging reads the RESOLVED engine's store and surfaces daemon failures; `absent` is concluded only when the daemon answered.

Not in scope (unchanged): the W3.6 overlay build engine (`overlay.go:51`, `#36`) and the W3.8 systemd-container init work.
